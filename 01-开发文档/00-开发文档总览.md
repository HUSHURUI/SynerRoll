## 1. 文档目的

本文服务于开发者、模型研究人员和产品维护人员，说明：

- SynerRoll 当前是什么、如何组织代码和数据；
- 用户从建模到计算和查看结果的完整流程；
- 多画布、组件、边界、时间层、任务和结果之间的关系；
- 当前实现与未来目标之间的界线；
- 如何继续增加组件、数学模型、指标、求解器和业务线。

本文描述的是长期目标系统。当前尚未实现或尚未闭环的能力会明确标记，避免把设计目标误认为现有功能。

## 2. 产品概述

SynerRoll 是一个综合能源优化建模与计算母机。它通过图形画布描述能源系统拓扑，通过组件参数和外部时序描述运行条件，通过 Julia/JuMP 构建优化模型，再将运行、灵活性、经济、碳和稳定性结果返回到桌面界面。

主要应用形态：

1. 内部科研人员进行优化模型开发、仿真验证和结果追踪；
2. 面向客户提供稳定、直观、可解释的方案测算和演示；
3. 从母机派生不同业务软件，例如运行仿真、在线预测决策控制、容量规划和专题评价产品。

核心质量目标是稳定、可解释、低资源开销、结果可追溯。系统不以深度权限管理和复杂操作审计为重点。

## 3. 功能全景

### 3.1 项目管理

- 创建、复制、打开、收藏和删除项目；
- 维护项目名称、说明、标签和基础信息；
- 管理一个项目中的多个画布；
- 保存项目公共时间层、边界、算法和求解器配置；
- 从内置场景或模板创建用户项目；
- 未来支持项目打包导入、导出与版本快照。

### 3.2 多画布建模

- 一个项目拥有 `workspace.canvases[]`；
- `activeCanvasId` 表示当前编辑画布；
- 每个画布独立保存节点、连接、视口、页面和显示配置；
- 一个画布可独立创建仿真任务或容量规划任务；
- 项目边界资源可被多个画布复用，绑定关系仍落实到具体组件。

### 3.3 组件库

当前组件库由 `config/component-library.json` 描述，包含组件显示信息、分类、端口、边界需求、公共参数、分层参数、规划属性和可用运行状态。

现有主要设备包括：

- 新能源：风机 WT、光伏 PV；
- 常规能源：煤电 CP、燃机 GP、热电联产 CHP、水电 HYDRO；
- 储能：电储能 ES、储氢 HS、飞轮 FS、抽蓄 PS、压缩空气 CS；
- 转换设备：电解槽 ET；
- 负荷：电负荷 ELOAD、氢负荷 HLOAD、热负荷 QLOAD；
- 外部系统：电网 GRID；
- 总线：电、热、氢等载能总线。

未来扩展电、热、冷、气、氢、氨、醇、碳以及源网荷储全体系，并在仿真业务线增加网络模型。

### 3.4 边界数据

边界描述组件外部不能完全由优化模型决定的时序条件，例如：

- 风速、辐照度、温度；
- 可用出力、出力系数；
- 电/热/氢负荷；
- 购售电价、计划或目标曲线；
- 其他资源、价格和环境条件。

系统根据画布组件推荐需要的边界，用户确认、替换或复用。一条边界可以绑定多个画布中的多个组件。

### 3.5 仿真任务

- 选择项目、画布、时间层、起止时间及在线/离线模式；
- 冻结项目与画布快照；
- 解析组件、连接和边界映射；
- 构建分时段 JuMP 模型；
- 调用 COPT 或备用求解器；
- 将变量、状态、trace、灵活性和经济结果写入任务数据库；
- 离线任务支持启动、取消、查看和显式清理；在线预测控制任务另行支持暂停、策略切换和恢复。

### 3.6 结果分析

- 任务概览；
- 设备出力和状态；
- 各载能平衡；
- 设备与系统灵活性；
- 经济评价；
- 碳排放；
- 供需稳定性和脆弱点；
- 原始变量、连接映射和求解 trace 的专家视图。

### 3.7 容量规划

- 自动识别可规划容量；
- 使用历史边界生成典型场景；
- 选择经济目标、技术约束和规划层；
- 搜索候选容量并执行运行仿真评价；
- 比较收敛、可行性、目标分解和约束余量；
- 将方案应用到项目版本并进行完整历史仿真。

## 4. 技术架构

### 4.1 前端

技术栈：Nuxt 4、Vue 3、TypeScript、Tailwind CSS、Vue Flow、ECharts、XLSX。

主要职责：

- 项目和多画布编辑；
- 组件参数及运行状态配置；
- 边界数据导入、处理和预览；
- 仿真和容量规划表单；
- 任务状态订阅；
- 时序、灵活性、经济和规划结果可视化；
- 通过 Nuxt server API 充当前端 BFF，屏蔽 Julia API 细节。

### 4.2 Nuxt BFF

目录：`server/api/v1/` 与 `server/utils/`。

主要职责：

- 提供 `/api/v1` 版本化接口；
- 保存和读取项目 JSON；
- 将边界、任务、规划和 ingest 请求转发给 Julia；
- 对前端统一错误结构；
- 后续负责后端地址发现、本地访问令牌和桌面进程协同。

### 4.3 Julia 计算后端

主要目录：

| 目录 | 职责 |
|---|---|
| `backend/components/` | 每类组件的结构、schema、模型、灵活性和 validation |
| `backend/core/` | 组件框架、公共类型、验证、灵活性核心 |
| `backend/services/` | 解析、模型构建、任务、边界、经济和灵活性服务 |
| `backend/services/capacity_planning/` | 变量识别、场景聚类、候选评估、优化和存储 |
| `backend/routes/` | 任务、容量规划和实时 ingest API |
| `backend/utils/` | 时序、数据库、预测和通用计算工具 |
| `backend/data/` | 本地运行数据库、项目边界、任务和规划产物 |

Julia 后端以 JuMP 为模型接口，COPT 为主要求解器，并应通过适配层支持至少一种开源 MILP 求解器。未来 SOCP/NLP 模型按派生业务线选择兼容求解器。

### 4.4 数据存储

目标存储边界如下：

| 数据 | 建议存储 | 说明 |
|---|---|---|
| 项目索引和配置 | 项目 JSON 或项目级配置文件 | 小型结构化数据，必须原子写入 |
| 画布 | 项目 `workspace.canvases[]` | 每画布独立节点、连接和显示配置 |
| 边界时序 | `data/projects/<projectId>/boundary.db` | 项目级共享时序真值 |
| 任务索引 | `tasks.db` | 状态、时间、错误、进度和产物位置 |
| 任务快照 | `data/tasks/<taskId>/project.json` | 保证结果可复现 |
| 任务结果 | `data/tasks/<taskId>/timeseries.db` | 时序、trace、灵活性和摘要 |
| 规划索引 | `capacity-planning.db` | 规划配置、评估和最佳结果索引 |
| 规划场景 | 规划目录下 SQLite/JSON | 典型日、权重和质量指标 |

大段时序不得同时以 JSON 数组和 SQLite 重复作为真值。JSON 只保存边界配置、series ID、单位、来源摘要、变换参数和版本哈希。

## 5. 核心数据模型

### 5.1 Project

项目至少包含：

- `id`、名称、说明、标签等元数据；
- `workspace.activeCanvasId`；
- `workspace.canvases[]`；
- `layerConfig`；
- `boundaries[]`；
- `algorithm`；
- `solverConfig`；
- `schemaVersion` 与更新时间。

项目保存时应进行 schema 校验、临时文件写入、落盘同步和原子替换，防止中断造成 JSON 损坏。

### 5.2 Canvas

每个画布包含：

- 稳定且唯一的 canvas ID；
- 名称和说明；
- 节点和边；
- 视口、网格、页面尺寸与显示设置；
- 组件—边界绑定；
- 最后修改时间。

跨画布复制节点时应生成新的节点、端口和边 ID，但可以继续引用同一项目边界 ID。

### 5.3 Component

组件实例由以下部分构成：

- 组件类型 key；
- 实例 ID、名称和画布位置；
- 端口及载能介质；
- 公共技术参数；
- 分时层参数与运行状态；
- 经济和规划参数；
- 边界 ID 列表；
- schema 版本。

前后端应从同一份组件 schema 生成表单、默认值和校验规则。Julia 特有的模型代码仍由组件模块维护。

### 5.4 Boundary

边界配置至少包含：

- ID、名称和 meaning；
- 单位、时区、时间分辨率与覆盖区间；
- 数据 series ID；
- 原始来源摘要和内容哈希；
- 列映射；
- 插值和变换管线；
- 随机 seed；
- 关联的画布和组件；
- 数据质量结果。

### 5.5 Task

任务至少记录：

- 项目 ID、画布 ID和快照哈希；
- 在线/离线模式；
- 目标时层、开始与结束时间；
- 状态、进度和当前模拟时刻；
- 求解器和模型版本；
- 产物目录；
- 分类错误码与解释；
- 创建、启动、完成和更新时间。

## 6. 多时间层运行规则

SynerRoll 的多时间层用于表示日前、日内、实时或其他尺度的层级计划。时间尺度原则上为 1 分钟及以上，上层计划可向下层传递离散状态和连续出力。

五种正式状态：

| 状态 | 是否使用上层离散状态 | 是否约束连续出力 | 是否在当前层建模 |
|---|---:|---:|---:|
| 独立运行 | 否 | 否 | 是 |
| 禁用 | 不适用 | 不适用 | 否 |
| 固定状态 | 是 | 当前层自由优化 | 是 |
| 调节出力 | 尊重上层停机等状态 | 在上层计划附近调节 | 是 |
| 完全跟随 | 是 | 完全跟随 | 是，但变量被固定/映射 |

层间规则必须显式处理：

- 上下层步长映射；
- 上层计划在下层时间点的展开；
- 充放电、启停和购售状态；
- SOC、库存和累计量的连续性；
- 暂停、恢复和跨日状态重建；
- 边界数据分辨率变化。

## 7. 边界数据工作流

### 7.1 推荐

组件 schema 声明需要或可接受的边界 meaning。新增组件或改变画布后，系统扫描缺失项并生成推荐。推荐不是强制创建，最终由用户确认。

### 7.2 导入

用户选择 CSV/Excel 等文件，指定：

- 时间戳列或起始时间；
- 数据列；
- 原始单位；
- 时区和分辨率；
- 目标 meaning 与名称。

系统必须检查重复时间、乱序、缺失、异常值、单位和时间覆盖。

### 7.3 变换

变换管线可包括插值、重采样、缩放、偏移、截断、随机分布和噪声。执行顺序和 seed 必须保存，确保任务能够复现。

### 7.4 关联

边界与组件为多对多。每次任务解析时，根据目标画布生成明确的 component—meaning—series 映射，并保存到任务快照。

## 8. 仿真任务工作流

### 8.1 创建

创建前校验：

- 画布拓扑与端口介质；
- 组件参数和状态组合；
- 必需边界及时间覆盖；
- 时间层映射；
- 求解器可用性；
- 数据目录可写和磁盘空间。

### 8.2 解析与构建

解析器从项目快照提取目标画布，形成 component、connection 和 mapping 数据。模型服务根据组件类型、时层状态和边界构造变量、约束和目标。

### 8.3 求解

任务按时间层和模拟时刻推进。模型以 MILP 为主，必要时使用 SOCP/NLP。供需平衡始终包含缺额和过剩松弛，以保证业务结果可解释。

### 8.4 状态机

离线目标状态：

`pending → queued → starting → parsing → building → solving → completed / failed / cancelling → cancelled / interrupted`

- cancel：终止计算并保留已有数据；
- interrupted：进程或服务异常中断，不承诺离线续算；
- cleanup/delete：只允许终态，关闭数据库、求解器和文件句柄后再清理目录与索引；
- pause/resume 不属于当前离线计算能力。

在线预测控制另有 `pausing/paused/switching/resuming` 状态，用于暂停一种在线策略、切换另一种策略或重新恢复，并按当前真实时间重建运行状态。

### 8.5 多进程隔离原则

最新业务决定已替代此前同进程方案。Julia 常驻 supervisor 只负责 API、队列、状态和资源调度；每个计算任务由独立 OS 进程执行，使用独立时序数据库、工作目录和 COPT/JuMP 会话。并发上限由 CPU、内存、求解器许可证和单任务线程数共同决定。一个 worker 阻塞或崩溃不得影响 API 和其他任务。

## 9. 在线与离线模式

### 9.1 离线

- 使用已有边界历史数据；
- 以最快求解速度推进；
- 只提供开始和终止，不提供暂停/恢复；
- 适合方案验证、规划和批量测试。

### 9.2 在线

- 模拟时间不得超前于真实时间；
- 持续接收第三方实际值和预测值；
- 所有输入先写入受控时序接口，再由模型读取；
- 暂停时模拟时间停止；恢复时跳到当前真实时间，并重建 SOC、库存、启停和其他状态；
- 可设置无固定结束时间，但必须进行数据库轮转和磁盘限制。

在线和离线共享组件、模型、结果与错误体系，仅在时钟、数据供给和恢复策略上不同。

## 10. 结果和可解释性

### 10.1 设备出力

显示每个组件的连续出力、离散状态、容量边界、计划值和实际优化值。普通视图使用业务名称，专家视图可显示变量名、UUID 和约束来源。

### 10.2 能量平衡与稳定性

按载能和总线展示供给、需求、转换、缺额和过剩。稳定性以供需平衡达标为中心，输出：

- 达标率；
- 缺额/过剩时段占比；
- 峰值、累计量和持续时间；
- 脆弱时间点、总线及原因；
- 松弛惩罚对目标的影响。

### 10.3 错误分类

界面必须区分：

1. 用户输入或操作错误；
2. 边界数据质量/覆盖错误；
3. 拓扑或组件规则错误；
4. 数学模型产生大量松弛；
5. 求解器超时、许可或数值错误；
6. 数据库、磁盘或程序异常。

## 11. 灵活性模块说明

灵活性是在基准运行结果上进行的后验评价：

- 计算各设备下一时段可提供的上、下调能力；
- 按现有公式聚合设备能力；
- 用 GRID/POI 可用交换空间截断系统供给；
- 与净负荷变化、计划/AGC 或用户给定需求比较；
- 计算裕度、缺额、达标率和设备贡献。

灵活性不负责重新优化生成调度指令，不扩展多 POI 和内部网络约束。现有灵活性说明和计算示例是正式公式基线。

## 12. 经济模块说明

经济模块分为两个层次：

1. **运行经济性**：根据任务时序计算燃料、购售能、可变运维、启停、碳和松弛等运行期成本与收益。
2. **项目全生命周期经济性**：叠加投资、固定运维、替换、残值、税、折现和项目现金流，计算总成本、NPV、IRR、LCOE 和回收期。

每个公式必须有：

- 输入字段与单位；
- 适用条件；
- 时间聚合方法；
- 现金流时点；
- 异常和不可计算条件；
- 公式版本；
- 独立算例和 Excel 导出校验。

## 13. 容量规划说明

容量规划采用典型场景上的候选方案仿真评价。未来支持七类目标，但每个目标只有在公式、输入和验证完整后才标记为可用。

关键规则：

- 优化变量可包含容量、台数、储能功率/能量等，但必须由组件 schema 明确声明；
- 离散台数和步长必须真正进入优化变量编码；
- 典型场景保留权重和聚类质量；
- 极端日不能只因权重小而被忽略；
- 储能等跨时段状态必须有明确的典型日衔接策略；
- 候选方案通过同一仿真引擎计算目标、松弛和技术指标；
- 最佳方案应用到新版本，避免静默覆盖用户正在编辑的项目。

## 14. API 分区

当前 Nuxt BFF 已按以下业务分区：

- `/api/v1/project`：项目、画布、时间层、算法、边界配置；
- `/api/v1/boundary`：导入、变换、提交、加载和删除；
- `/api/v1/task`：创建、列表、状态、数据、trace、灵活性、经济、取消和删除；
- `/api/v1/capacity-planning`：表单、校验、场景、任务、进度、结果和应用；
- `/api/v1/ingest`：在线任务和项目边界时序写入。

后续需统一：

- 请求/响应 schema；
- 稳定错误码；
- API 版本；
- 幂等性；
- 大数据分页/降采样；
- WebSocket/SSE 的唯一实时通道；
- 本地或服务器部署的访问控制。

## 15. 组件扩展规范

新增组件至少完成：

1. 在组件库 schema 定义名称、分类、端口、参数、单位、边界需求、规划变量和状态矩阵；
2. 在 Julia 组件目录定义类型与默认值；
3. 实现模型变量、约束和目标函数贡献；
4. 实现特殊 validation；
5. 实现结果字段和必要的灵活性/经济接口；
6. 增加独立公式说明和最小算例；
7. 增加正常、边界、不可行和跨时层测试；
8. 验证前端表单、任务解析、求解与结果展示闭环。

只有完成上述闭环的组件才可在正式组件库中标记为“可用”。

## 16. 求解器扩展规范

模型代码不应直接依赖 COPT 特有 API。求解器适配层负责：

- 创建 optimizer；
- 配置时间限制、gap、线程和日志；
- 检查许可与能力；
- 映射统一终止状态；
- 返回最优、可行、超时、不可行和数值错误；
- 根据模型类型选择 COPT 或开源求解器。

备用求解器至少覆盖 LP/MILP。SOCP/NLP 能力按具体业务线声明，不承诺所有模型可由同一求解器运行。

## 17. 开发和运行环境

目标发行包应内置或自动管理固定版本的前端运行时、Julia 环境和依赖，使客户无需手工搭建开发环境。

当前源码环境存在两个已知前置问题：

- `backend/Project.toml` 依赖项不是合法 Julia UUID，不能作为可复现项目环境；
- 当前工作区未安装前端依赖，且 package scripts 没有测试、lint 和 typecheck 命令。

因此，正式运行说明必须在修复依赖清单、生成锁文件、建立启动脚本和完成干净机器验证后定稿。开发环境应提供：

- 一键依赖检查；
- 前端、Julia 和联合启动；
- 数据目录与端口配置；
- 求解器可用性检查；
- 健康检查；
- 示例项目和 smoke test；
- 日志与诊断包位置。

## 18. 当前限制

- 多画布结构已存在于项目数据，但部分 API、解析和页面仍需逐项验证是否始终使用 canvas ID；
- 当前同进程任务执行架构需要改为 supervisor/独立 worker；
- 离线页面仍有旧 pause/resume 状态和入口需要清理，在线能力尚未实现；
- 组件运行状态 validation 不完整；
- 经济全生命周期公式尚未建立；
- 容量规划部分目标仍是界面/配置方向而非完整计算能力；
- 稳定性尚无正式版本化公式；
- COPT 之外的备用求解器尚未形成统一适配；
- 网络模型尚未进入当前核心组件框架；
- 依赖、测试、迁移、备份和安装流程尚未达到稳定发行标准。

## 19. 术语表

| 术语 | 含义 |
|---|---|
| 项目 | 保存多个画布和公共配置的顶层业务对象 |
| 画布 | 一个可独立建模、仿真或规划的系统拓扑 |
| 组件 | 画布中的设备或总线实例 |
| 边界 | 外部输入时序及其与组件参数的绑定 |
| 时间层 | 日前、日内、实时等不同优化尺度 |
| 任务 | 某项目快照、画布和计算配置的一次执行 |
| 松弛 | 为保持模型可解而引入的缺额、过剩或违约变量 |
| 灵活性 | 基准运行点之后可提供的上、下调能力 |
| POI | 系统与外部电网交换的并网点 |
| 容量规划 | 通过场景仿真和优化搜索设备容量的过程 |
| 母机 | 可派生多个业务软件的公共建模与计算平台 |

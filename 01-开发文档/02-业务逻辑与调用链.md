# 业务逻辑与调用链

## 1. 分层调用原则

标准调用方向：

`Vue 页面 → composable → Nuxt /api/v1 BFF → Julia route → service/core/component → SQLite/文件 → DTO → 页面`

禁止反向依赖：组件模型不读取 Vue 状态；Julia service 不依赖页面字段名称；图表不直接读取 SQLite；页面不直接拼 Julia 地址。

## 2. 项目列表与项目保存

### 读取项目

1. `app/pages/project.vue` 调用 `useProjectApi().listProjects()`。
2. `composables/api/useProjectApi.ts` 请求 `GET /api/v1/project`。
3. `server/api/v1/project/index.get.ts` 调用 `server/utils/project-store.ts`。
4. project-store 读取 `server/data/projects.json`，返回 ProjectSummary。
5. 页面使用 `ProjectCard.vue` 展示。

### 保存多画布

1. `app/pages/editor/[projectId].vue` 维护当前 Project/CanvasWorkspace。
2. `CanvasWorkspace.vue` 发出节点、边、视口和页面配置变更。
3. editor page 将变更合并到 `workspace.canvases[]`，并由 `state/editor.ts` 记录 undo/redo 快照。
4. 保存时调用 `useProjectApi().saveCanvas(projectId, { workspace })`。
5. BFF `server/api/v1/project/[projectId]/canvas.put.ts` 更新项目。
6. project-store 写回 projects.json。

关键不变量：

- `activeCanvasId` 必须存在于 `canvases[]`；
- canvas ID、node ID、edge ID 在项目内唯一；
- 保存一个画布不能覆盖其他画布；
- 任务/容量规划必须显式使用 canvasId，不能只依赖 activeCanvasId；
- 写项目文件应使用原子替换和更新版本检查。

## 3. 画布节点与连线

### 新增组件

1. `LibrarySidebar.vue` 从 `config/component-meta.ts` 读取 ComponentDefinition。
2. 拖到 `CanvasWorkspace.vue` 时，`utils/canvas.ts` 创建节点、默认 style、ComponentMeta 和端口配置。
3. 节点由 `CanvasNode.vue` 渲染。
4. `PropertiesPanel.vue` 根据 ComponentDefinition 的字段定义生成参数表单。

### 建立连线

1. 用户连接 Vue Flow Handle。
2. `CanvasWorkspace.vue` 读取源/目标端口 direction 与 medium。
3. `utils/canvas.ts` 校验、创建 FlowEdge，并按 `MEDIUM_EDGE_STYLES` 设置颜色。
4. 总线端口由 `BUS_PORT_ID_PATTERN`、side、suffix 规则动态管理。
5. 保存任务后，`backend/services/parse_service.jl` 再次校验 edge medium、嵌套总线和名称。
6. parse service 生成 ConnectionRecord，供 `model_service.jl` 建立总线平衡。

前端校验用于即时体验，Julia 校验才是计算安全边界；二者必须共享规则但不能只信任前端。

## 4. 边界配置链路

### 配置保存

1. `app/pages/boundary/[projectId].vue` 加载 Project 和 boundaries。
2. 用户创建边界、选择 meaning、组件关联、插值/随机配置。
3. `utils/boundary-sync.ts` 同步 boundary.relatedComponents 与节点 ComponentMeta.boundaryIds。
4. `useProjectApi().saveBoundaries()` 调用 `PUT /api/v1/project/{id}/boundary` 保存配置。

### 文件导入与变换

1. 页面请求 `/api/v1/boundary/import`。
2. Nuxt BFF 转发到 Julia `/api/boundary/import`。
3. `backend/server.jl` route 解析请求，调用 boundary service/CSV DataFrame 读取。
4. 返回列、数值、时间戳与预览。
5. transform 请求执行分层重采样、插值、随机化或噪声。
6. submit 将 series 和 boundary config 写入 `data/projects/<projectId>/boundary.db`。

### 任务 seed

1. `simulation_runner._inject_boundary_phase` 根据 task 的 projectId/canvasId/layer 解析绑定。
2. `boundary_service.seed_task_boundary_data` 从项目 boundary.db 读取。
3. 将目标范围数据复制/转换到任务 timeseries.db。
4. 组件模型以 data key 读取边界值。

故障排查顺序：页面请求体 → BFF body → Julia route → boundary config → series meta/data → task seed key → component lookup。

## 5. 创建仿真任务

1. 任务页或编辑器调用 `useTaskApi.createTask(CreateTaskRequest)`。
2. `server/api/v1/task/create.post.ts` 根据 projectId 从 project-store 读取完整项目。
3. BFF 把 `projectJson` 与 canvasId、layerId、mode、时间等转发到 Julia `/api/task/create`。
4. 当前 `backend/routes/task.jl`：
   - 生成 task ID；
   - 创建 `data/tasks/<id>/`；
   - 写 `project.json` 快照；
   - `insert_task!` 写 tasks.db；
   - `spawn_task` 在同一 Julia 进程启动异步任务。
5. 页面获得 ComputeTask，转到任务列表并订阅 WebSocket。

创建前应校验项目、canvasId、layerId、时间格式、边界覆盖和 solver；当前部分校验发生在异步任务内部，未来应把可快速判断的错误前移。

## 6. 仿真运行链路

`backend/services/simulation_runner.jl` 是总编排器：

1. `_parse_phase` 调用 `parse_project`；
2. parse service 写 `component.json`、`connection.json`、`mapping.json`；
3. `_prepare_build_phase` 加载组件和连接，构造总线 nodes；
4. `_inject_boundary_phase` 准备任务时序；
5. `run_task` 或 `run_single_layer_task` 遍历时间层/时间点；
6. `model_service.build_model_tracked` 实例化组件并构造 JuMP 模型；
7. 各组件 `model.jl/model-common.jl` 加变量、约束和目标项；
8. model service 添加电/热/氢总线平衡和缺额/过剩松弛；
9. `solve_model` 调用 optimizer；
10. 组件结果和 slack 写入 task timeseries.db；
11. tracked code/solve trace 写入 generated 目录和 trace 表；
12. `_evaluate_flexibility_after_solve!` 进行后验灵活性评估；
13. 任务状态更新为 completed/failed/cancelled。

上述是当前链路，不是目标架构。最新决定要求改为：BFF→TaskService→supervisor 入队→独立 worker 进程读取不可变快照→worker 私有数据库/代码/trace→worker 事件回传 supervisor→tasks.db 和 WebSocket。每个任务独享工作目录、时序库和 COPT/JuMP 会话；并发由资源令牌控制。

## 7. 任务状态与实时消息

### 状态真值

- 持久状态：`backend/data/tasks.db`；
- 当前运行上下文：`TASK_CONTEXTS[taskId]`；目标改为 supervisor 中的 worker/process handle，不保存 JuMP 模型；
- 页面缓存：前端仅用于展示，不是最终真值。

### 状态接口

- list：`GET /api/task/list`；
- state：`GET /api/task/{id}/state`；
- cancel：`POST /api/task/{id}/cancel`；
- delete：`DELETE /api/task/{id}`；
- WebSocket：`/ws/task/*`。

离线目标状态机增加 queued、starting、cancelling、interrupted，但不增加 paused；在线预测控制另行定义 paused/switching/resuming。REST、WebSocket、tasks.db、worker 协议和 UI 标签必须使用同一 schema。

## 8. 任务结果链路

### 普通时序

`tasks/index.vue → useTaskApi.getData → BFF → GET /api/task/{id}/data → timeseries_utils.query_ts → TaskDataResponse → 图表`

查询条件包括 layerId、varName、sourceId、remark。结果主键语义由 `source_id|var_name|remark#layer_id` 构成。

### Connection

`getConnection → /connection → task connection.json → busLabel/busCode/variables`，用于能量流和结果分组。

### Trace

`getTraceSteps/getTraceData → solve_trace_meta/data`，用于按求解步查看完整变量快照。trace 应是专家/调试能力，避免默认全量记录。

### 经济结果

`getEconomy → routes/task.jl → economy_evaluation_service.evaluate_task_economy → economy_calculator → EconomyEvaluationResult`。

当前主要是运行成本，完整生命周期指标应由后续经济模块提供版本化 DTO。

## 9. 灵活性调用链

1. simulation runner 在基准求解后触发 flexibility evaluation。
2. `flexibility_baseline_adapter.jl` 从 task DB 读取基准出力、状态和边界。
3. 每个组件 `flexibility.jl` 调用 `flexibility_utils.jl` 形成 ComponentFlexibilityResult。
4. `flexibility_supply_service.jl` 聚合设备供给，并由 GRID/POI 可用空间截断。
5. `flexibility_requirement_service.jl` 形成净负荷、AGC/计划或用户需求。
6. `flexibility_margin_service.jl` 计算裕度、缺额和摘要。
7. `flexibility_result_service.jl` 持久化 period/summary。
8. `GET /api/task/{id}/flexibility` 返回页面。

设计边界：仅后验评估；不回写基准调度；不做网络约束、多 POI 或可执行再调度。

## 10. 容量规划调用链

### 表单与变量

1. 页面调用 `/capacity-planning/form-schema`。
2. BFF 注入项目快照。
3. `variable_detector.detect_capacity_variables` 找目标 canvas。
4. 读取 `component-library.json` 中 capacity 的 planning 元数据。
5. 返回可优化/固定变量、范围、步长和 warning。

### 典型场景

1. `scenario_reducer.load_ts_boundary_features` 从 boundary.db 读取选定 series。
2. 对齐完整日，处理缺失，归一化。
3. KMeans/KMedoids 生成 representative date、members、weight、quality。
4. planning store 保存 scenarios 和 per-planning scenarios.db。

### 优化

1. `planning_manager.start_capacity_planning!` 建立 PlanningContext。
2. `optimization_runner.run_capacity_optimization!` 生成候选。
3. `candidate_snapshot.apply_capacity_candidate` 只修改目标 canvas 的容量字段。
4. `simulation_evaluator.evaluate_snapshot` 对每个典型场景运行模型。
5. `economic_evaluator.evaluate_economics` 计算 fitness。
6. planning store 保存 evaluation、best 和 result。
7. 前端轮询/读取进度并画收敛曲线。

### 应用并仿真

BFF `/apply-and-simulate` 校验 projectUpdatedAt，应用最佳容量，再调用任务 create 对完整历史数据进行 offline 验证。未来应优先生成方案版本，避免静默覆盖。

## 11. 在线 ingest 链路

- 项目边界：`POST /api/v1/ingest/project/{projectId}/boundary` → Julia ingest route → boundary.db merge；
- 任务时序：`POST /api/v1/ingest/ts/{taskId}` → Julia ingest route → task timeseries.db merge；
- 在线 runner：每步等待真实时钟，读取最新实际/预测/计划 series，求解后写结果。

未来必须补齐鉴权、幂等、乱序、补传、数据新鲜度和暂停恢复。所有外部数据必须通过 ingest/service 写入，不允许页面或第三方直接写 SQLite。

## 12. 项目删除链路

当前 BFF 删除项目配置和 boundary 目录，但任务和容量规划数据可能成为孤儿。目标删除流程：

1. 查询项目关联的运行任务并阻止或取消；
2. 选择只删项目/连历史一起清理；
3. 关闭项目 boundary store；
4. 删除项目配置与数据；
5. 按策略清理或标记任务、规划记录；
6. 返回实际删除清单。

客户展示产品建议提供二次确认；开发环境可提供清空测试数据命令。

# 数据结构与接口契约

## 1. 真值归属

| 数据 | 唯一真值 | 允许缓存 | 禁止 |
|---|---|---|---|
| 项目元数据/多画布拓扑 | 每项目独立 manifest/JSON | 前端当前编辑副本 | 所有项目共写一个大 JSON |
| 边界时序 | 项目边界 SQLite | 前端图表分页数据 | projects.json 保存可参与计算的大数组 |
| 任务控制状态 | 全局 tasks.db（supervisor 单写） | WebSocket/UI | worker 和页面各自改状态 |
| 单任务结果/trace | `tasks/<taskId>/` 数据库和归档 | 页面查询缓存 | 结果写回画布或跨画布共享 |
| 容量规划任务 | planning 控制库 + 任务工作目录 | UI 草稿 | 直接覆盖项目且无方案快照 |
| 组件元数据 | 版本化 Component Schema | 生成的 TS/Julia 静态产物 | 前后端人工复制同一枚举 |

## 2. 标识与绑定

- `projectId`：项目稳定 ID；移动目录不改变。
- `canvasId`：项目内画布稳定 ID。
- `componentId/nodeId`：画布内实例 ID；同类型组件不能用 componentKey 代替。
- `componentKey`：组件类型，如 WT、PV、ES；不是实例 ID。
- `boundaryId`：项目级边界对象 ID，可被同项目多个画布组件引用。
- `taskId`：一次不可变计算输入的运行 ID。
- `planningTaskId`：一次容量规划搜索；候选方案另有 candidateId。

每个计算必须绑定一个 `projectId + canvasId`。画布之间允许引用同一项目边界，但计算快照、任务数据库、结果、trace、代码和经济结果完全隔离。

## 3. 项目建议结构

```json
{
  "schemaVersion": 2,
  "id": "project-...",
  "name": "...",
  "workspace": {
    "activeCanvasId": "canvas-ui-only",
    "canvases": [
      {
        "id": "canvas-...",
        "name": "方案A",
        "nodes": [],
        "edges": [],
        "viewport": {},
        "display": {}
      }
    ]
  },
  "boundaries": [
    {
      "id": "boundary-...",
      "meaning": "power",
      "storeRef": "boundary.db#boundary-...",
      "meta": {}
    }
  ],
  "layerConfig": { "layers": [] },
  "algorithm": {},
  "solverConfig": {}
}
```

`activeCanvasId` 只服务 UI 恢复，任务创建必须显式给 canvasId。

## 4. 任务输入快照

任务创建时生成不可变 snapshot：

- 项目/画布 ID 与名称；
- 所选画布 nodes/edges；
- 画布引用边界的版本/hash；
- layerConfig、algorithm、solverConfig；
- 组件 schemaVersion/schemaHash；
- 软件版本、worker 协议版本、求解器版本；
- 任务模式、时间范围、目标层；
- 创建人输入的任务名和业务标签。

`params_hash` 对规范化快照计算，不包含 UI viewport、更新时间等非计算字段。相同 hash 可用于比较，不代表自动复用结果。

## 5. API 分层

### 项目与画布

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST | `/api/v1/project` | 列表/新建项目 |
| GET/PUT/DELETE | `/api/v1/project/{projectId}` | 项目元数据 |
| GET/PUT | `/api/v1/project/{projectId}/canvas` | 当前接口保存 workspace；目标应支持 canvas 子资源 |
| GET/PUT | `/api/v1/project/{projectId}/algorithm-config` | 算法和求解器专用 DTO |
| PUT | `/api/v1/project/{projectId}/layer-config` | 时层配置 |

多画布稳定后建议增加：

```text
GET  /project/{projectId}/canvas/{canvasId}
PUT  /project/{projectId}/canvas/{canvasId}
POST /project/{projectId}/canvas
DELETE /project/{projectId}/canvas/{canvasId}
```

### 边界

当前 BFF 有 load/import/transform/submit/delete。目标契约要求所有计算数据从 SQLite 返回；响应分页或按时间窗，不能把整个数组塞入项目详情。

### 普通任务

当前 create/list/state/data/connection/trace/economy/flexibility/cancel/delete 基本齐全。目标新增 queue/resource/diagnostics；离线 UI 只开放开始/终止，现有 pause/resume 接口先保留并说明为在线预留。在线开发时再决定复用现有接口还是放到 `/online-task/{id}/...`，不能让预留接口冒充已实现能力。

### 容量规划

当前 form-schema、validate、scenarios/preview、task CRUD、config、start、result、cancel、apply-and-simulate 形成完整骨架。所有请求需补 canvasId，并固化规划方案快照。

## 6. 统一响应

当前 TypeScript 使用 `ApiResponse<T>{success,data,message}`。目标再增加：

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "MODEL.PORT_MEDIUM_MISMATCH",
    "message": "...",
    "details": {},
    "traceId": "...",
    "retryable": false
  }
}
```

列表响应统一 `items,total,cursor/offset`；时间序列统一 `series/rows,nextCursor`；导出接口返回文件描述而不是把巨量 CSV 嵌入 JSON。

## 7. 类型漂移清单

- `UpdateAlgorithmConfigRequest` 只含 algorithm，但真实请求还有 solverConfig；必须改为专用 DTO。
- `BoundaryMeaning` 缺 heat/hydrogen，而 Julia 和组件已使用；必须由共享 schema 生成。
- `InterpolateType`/`RandomDistribution` 声明能力多于 UI 可选能力；需能力接口或删除未实现项。
- 旧 `SimulationStatus` 与新 `TaskStatus` 不同；离线、在线、容量规划应各有明确状态机并共享基础终态语义。
- `BoundaryItem.rawData` 与 `BoundaryRawData`、transformedData 重复结构；前者应删大数组，仅留 storeRef/meta。

## 8. SQLite 规范

- 每个数据库必须有 `schema_version`；迁移脚本只升不降，并有事务。
- tasks.db 由 supervisor 单写；worker 只写任务私有库。
- 所有连接通过 repository/store 获取和关闭；route 不缓存 SQLite.DB。
- 时间戳统一 ISO-8601 + 明确时区；内部建议 UTC，UI 显示 Asia/Shanghai。
- 数值列记录 unit 或引用 schema 中的稳定 unitKey。
- 任务完成后执行 integrity check、checkpoint/WAL 收口和 manifest hash。

建议任务目录：

```text
tasks/<taskId>/
  manifest.json
  input/snapshot.json
  data/timeseries.db
  data/result.db
  logs/worker.log
  generated/index.json
  generated/chunks/*.zst
  trace/index.sqlite
  trace/chunks/*.zst
  diagnostics/
```

## 9. 版本与兼容

每个持久化对象至少记录：`schemaVersion`、`createdByVersion`、`updatedByVersion`。当前测试数据无需建设复杂无损迁移，但新正式版本开始必须：

1. 读取时判断版本；
2. 支持已发布版本到当前版本的迁移；
3. 迁移前备份 manifest/数据库；
4. 迁移后做结构和关键计数校验；
5. 失败时保留原文件并给出可操作错误。

## 10. 契约测试

- TypeScript 请求 fixture 可被 Julia DTO 读取；
- Julia 响应 fixture 通过 TypeScript runtime schema；
- Component Schema 代码生成前后 hash 一致；
- project/canvas/boundary/task/planning 各有最小 fixture；
- heat/hydrogen、多画布、任意层数和极端数值必须在 fixture 中出现；
- 删除旧字段前先检索代码、数据、模板和测试中的所有使用点。

# 故障定位手册

## 1. 定位原则

先确定 `projectId + canvasId + taskId + layerId + simTime`，再按调用链向下。不要先在 2000 行页面内全文试错。任何故障报告至少附：操作入口、对象 ID、时间、状态、错误码、最近日志和是否可复现。

## 2. 故障入口表

| 用户现象 | 第一定位点 | 第二定位点 | 数据证据 |
|---|---|---|---|
| 项目打不开/保存丢失 | `server/utils/project-store.ts` | project API route、types/project.ts | 项目 manifest/JSON、schemaVersion |
| 画布切换后内容错 | editor 页面/CanvasWorkspace | canvas route、snapshot builder | projectId、两个 canvasId、workspace |
| 连线失败/介质错误 | CanvasNode/CanvasWorkspace | Component Schema、parse_service | source/target port、medium |
| 边界导入失败 | boundary 页面 | boundary BFF→Julia route/service | boundaryId、源列、SQLite row count |
| 边界图和计算不同 | boundary data API | 任务 seed、任务私有 DB | boundary hash、snapshot hash |
| 任务一直 pending | tasks 页面 | supervisor scheduler | queue position、resource token |
| API 被计算拖死 | health | worker/supervisor 隔离 | API latency、worker pid |
| 任务构建失败 | task state/diagnostics | simulation_runner→model_service→component | componentId、layerId、生成代码 |
| 求解不可行 | solver outcome | slack、能量平衡、组件校验 | conflict/IIS、slack series |
| 结果缺变量 | data route | ResultBinding、写库阶段 | variable label、row count |
| 灵活性不正确 | flexibility route | baseline adapter→component→system aggregate | baseline/up/down、POI 模式 |
| 容量方案不合理 | planning result | scenarios→candidate→economic evaluator | 变量上下界、权重、现金流 |
| 删除任务失败 | delete route | store registry→filesystem | 打开句柄、目录、终态 |
| WebSocket 无更新 | useTaskWebSocket | WS route/subscriber/supervisor event | URL、taskId、seq、最后心跳 |

## 3. 项目与多画布排查

1. GET 项目，确认项目存在且 schemaVersion 可读；
2. 在 `workspace.canvases` 中确认目标 canvasId；
3. 检查 nodes/edges 引用完整、边的 source/target 在同一画布；
4. 确认任务记录的 canvasId，不使用 activeCanvasId 代替；
5. 打开任务 snapshot，比较画布节点数、边数和 hash；
6. 若同项目另一画布结果串入，检查查询是否只按 projectId 过滤。

## 4. 边界排查

1. 项目 JSON 只看元数据/引用，不以其中数组判断真实值；
2. 查询项目边界 SQLite 的 boundaryId、meaning、时间范围、步长和点数；
3. 检查 heat/hydrogen 等 meaning 是否通过共享 schema；
4. 检查组件 boundaryIds 是否存在且介质匹配；
5. 比较任务 snapshot 的 boundary version/hash；
6. 检查 seed 后任务私有 DB 的 label 和行数；
7. 检查变换算法、缺失值、时区和时间层长度。

## 5. 任务排查

### pending/queued 不推进

检查 supervisor 是否 ready、队列位置、并发上限、COPT 许可证令牌、CPU/内存令牌、worker spawn 错误。不要直接把状态改成 running。

### starting 后失败

检查 Julia 可执行文件、Project/Manifest、worker 协议版本、schemaHash、工作目录权限和 solver license。

### parsing/building 失败

从 diagnostics 中取得 componentId/layerId；对照 task snapshot、`parse_service.jl`、`model_service.jl`、对应组件的 validation/model-common/model。生成 Julia 文件是关键审计证据，不删除。

### solving 无进度

区分 solver 正常长时间求解、无心跳、心跳存在但无 progress。查看 worker CPU/RSS、COPT 日志、模型规模、数值尺度。取消时先发送协作式 cancel，超时再终止 worker 进程。

### 单任务崩溃影响其他任务

这是 R10 未关闭的证据。记录 supervisor pid、所有 worker pid、各 taskId 和 API health；确认求解是否仍在控制面进程或共享全局模型/store。

## 6. 模型不可行排查顺序

1. 输入结构：空画布、孤立节点、端口介质不匹配；
2. 边界：缺失、时间范围不足、单位/符号错误；
3. 组件状态：disabled/fixed/full_follow 与边界冲突；
4. 容量和上下界：负值、min>max、效率越界；
5. 能量平衡：供需、储能初末、网络交换边界；
6. 多时层映射：forward、step、计划跟随窗口；
7. 数值尺度：big-M、slack penalty、容差；
8. 求解器：状态、IIS/conflict、time limit、license。

松弛用于解释缺额/过剩，不可把所有输入错误静默变成一个有 slack 的“成功”。

## 7. 结果与 trace 排查

- 普通结果：task data API→任务 DB→结果写入→ResultBinding。
- Connection：确认边方向、变量符号和聚合时刻一致。
- Trace：先查 step 索引，再懒加载该步骤分片；不得遍历全部压缩文件。
- 经济：确认 costType、单位、是否 inObjective、收入符号和 slack penalty。
- 灵活性：确认基线时刻、up/down 方向、设备能力之和、POI 限制和系统汇总。
- 容量：确认候选 snapshot、典型场景权重、运行成本折算和生命周期现金流。

## 8. 前端故障排查

- 按浏览器 Network 找失败请求，记录路径、请求体、响应错误码；
- 对照 `composables/api`，确认没有走旧 simulation/export 链路；
- 对照 `types/api.ts` 与服务端 DTO，禁止用断言掩盖字段缺失；
- WebSocket 使用 runtimeConfig 的实际 URL，并确认 seq 连续；
- 状态标签只从共享 status map 获取；
- 页面显示值与 SQLite 不同，优先排查缓存/旧 projects.json 数组。

## 9. 清理与恢复

- cancel：停止计算，不删除任何数据；
- cleanup：只允许终态，先关闭 DB/文件/solver，再删目录，最后改索引；
- 已知的任务索引/目录不一致由人工删除测试文件造成，按业务回复排除，不作为产品整改项；
- 服务重启：离线运行中任务标 interrupted/failed；在线任务按在线恢复协议处理；
- 历史代码/trace：默认保留，可归档压缩；只有用户显式清理才删除。

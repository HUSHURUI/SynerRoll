# BUG-001：边界数据提交后编辑器卡顿、任务创建卡死

> 修复日期：2026-09-16
> 状态：已定位、已修复、待回归验证
> 严重程度：P0 — 阻塞核心建模与计算流程
> 影响范围：所有导入了 8760 长度边界数据的项目

---

## 1. 问题描述

**用户操作路径**：

1. 进入边界配置页，导入三组 8760 长度的时序数据（全年逐小时数据）
2. 点击提交，数据写入 boundary.db
3. 返回编辑器页面，拖拉拽组件、填写参数等常规操作出现明显卡顿
4. 进入仿真计算页，点击按钮创建计算任务后，后端完全卡住几乎无响应

**预期行为**：边界数据提交后应与前端、编辑器和任务创建完全解耦，不影响正常使用。

---

## 2. 初步分析与嫌疑假设

根据开发文档追踪边界数据的完整链路：

```
前端 boundary 页
  → POST /api/v1/boundary/submit → BFF → Julia /api/boundary/submit → 写 boundary.db
  → saveCurrentFormToBoundary() → 将 rawData/transformedData 存入 project.boundaries
  → PUT /api/v1/project/{id}/boundary → BFF → projects.json
```

由此形成三个嫌疑假设：

| 编号 | 假设 | 对应症状 | 初始置信度 |
|---|---|---|---|
| H1 | `projects.json` 内嵌了 rawData/transformedData 全量数组，文件膨胀到数十 MB | 编辑器卡顿 + 任务创建卡死 | ⭐⭐⭐⭐⭐ |
| H2 | Julia 侧 `write_lock` 全局锁在逐行 INSERT 8760 行期间阻塞所有其他 DB 操作 | 后端无响应 | ⭐⭐⭐⭐ |
| H3 | boundary seed 阶段无仿真时间范围时数据被复制一倍（8760→17520），内存/IO 飙升 | 任务创建卡死 | ⭐⭐⭐ |

---

## 3. 调试方案：如何设计日志定位问题

核心思路：**对每个假设，在关键路径上插入计时和体积度量日志**，用数据排除或确认假设。

### 3.1 日志点设计总览

| 日志标记 | 文件 | 监控目标 | 对应假设 |
|---|---|---|---|
| `[STORE]` | `server/utils/project-store.ts` | projects.json 每次写入总大小、每个项目 boundaries 的 rawData/transformedData 点数 | H1 |
| `[SUBMIT]` | `backend/server.jl` | 边界提交总耗时、每条 delete/set_ts 耗时 | H2 |
| `[LOCK]` | `backend/utils/timeseries_utils.jl` | `set_ts`/`get_ts`/`query_ts` 的锁等待时间和写入耗时 | H2 |
| `[SEED]` | `backend/services/boundary_service.jl` | 无仿真时间范围时的数据复制倍数、seed 写入耗时 | H3 |
| `[TASK-CREATE]` | `server/api/v1/task/create.post.ts` | 创建任务时发送给 Julia 的 project JSON 体积 | H1 |

### 3.2 各日志点详细实现

#### 日志点 1：[STORE] — projects.json 写入体积

**文件**：`server/utils/project-store.ts` — `writeProjectsUnlocked` 函数

**思路**：每次写入 projects.json 前，序列化 boundaries 数组并输出大小。如果某个项目的 boundaries JSON 超过 10 KB，逐条打印 rawData 和 transformedData 的点数。

**实现**：
```typescript
const writeProjectsUnlocked = async (projects: Project[]): Promise<void> => {
  await mkdir(dataDirectory, { recursive: true })
  const jsonStr = JSON.stringify(projects, null, 2)
  console.log(`[STORE] writing projects.json: ${(jsonStr.length / 1024).toFixed(1)} KB, projects=${projects.length}`)
  for (const p of projects) {
    const boundaryBytes = JSON.stringify(p.boundaries ?? []).length
    if (boundaryBytes > 10000) {
      console.log(`[STORE]   project ${p.id} boundaries JSON: ${(boundaryBytes / 1024).toFixed(1)} KB`)
      for (const b of (p.boundaries ?? [])) {
        const bAny = b as any
        const rawLen = bAny.rawData?.values?.length ?? 0
        const transLayers = bAny.transformedData?.layers ?? []
        if (rawLen > 100 || transLayers.length > 0) {
          const transPoints = transLayers.reduce((s: number, l: any) => s + (l.values?.length ?? 0), 0)
          console.log(`[STORE]     boundary ${b.id} rawData=${rawLen}pts transformedData=${transPoints}pts`)
        }
      }
    }
  }
  await writeFile(dataFile, jsonStr, 'utf8')
}
```

#### 日志点 2：[SUBMIT] — Julia 边界提交耗时

**文件**：`backend/server.jl` — `/api/boundary/submit` 路由

**思路**：在 submit 路由入口记录时间戳，对每个 `delete_ts_by_source_id` 和 `set_ts` 调用计时，最后输出总耗时。

**实现**：
```julia
@post "/api/boundary/submit" function (req)
    t_submit_start = time()
    # ...
    @info "[SUBMIT] received boundaries count=$(length(boundaries))"
    # 每次 delete：
    t_del = time()
    delete_ts_by_source_id(db_path=db_path, source_id=bid, remark="planned")
    @info "[SUBMIT] deleted old data" bid elapsed_s=round(time()-t_del, digits=3)
    # 每次 set_ts：
    t_set = time()
    set_ts(db_path, label, ts)
    @info "[SUBMIT] set_ts done" label points=length(values) elapsed_s=round(time()-t_set, digits=3)
    # 总计：
    @info "[SUBMIT] total done" stored_count=length(stored_keys) total_s=round(time()-t_submit_start, digits=3)
```

#### 日志点 3：[LOCK] — SQLite write_lock 锁等待监控

**文件**：`backend/utils/timeseries_utils.jl` — `set_ts`、`get_ts`、`query_ts` 函数

**思路**：在 `lock(store.write_lock)` 前记录时间，获得锁后计算等待时间。超过 50ms 即输出警告。同时记录写入操作的耗时和数据点数。

**实现**（以 `set_ts` 为例，`get_ts`/`query_ts` 同理）：
```julia
function set_ts(db_path::String, data_key::String, ts::TimeSeries)
    store = get_store(db_path)
    t0 = time()
    lock(store.write_lock) do
        t_locked = time()
        wait_s = t_locked - t0
        if wait_s > 0.05
            @warn "[LOCK] set_ts: lock wait" data_key wait_s=round(wait_s, digits=3)
        end
        _write_ts(store, data_key, ts)
        @info "[LOCK] set_ts: write done" data_key points=length(ts.values) write_s=round(time()-t_locked, digits=3)
    end
end
```

#### 日志点 4：[SEED] — boundary seed 数据复制监控

**文件**：`backend/services/boundary_service.jl` — `seed_task_boundary_data` 函数

**思路**：在"无仿真时间范围、复制一倍"分支输出原始点数和复制后点数。在批量写入前后计时。

**实现**：


**文件**：`backend/services/boundary_service.jl` — `delete_ts_by_source_id` 函数

## 4. 日志结果

### 4.1 Julia 侧 — submit 耗时正常，无锁竞争

```
[SUBMIT] received boundaries count=5
[SUBMIT] deleted old data  bid="b_mu3tv0j8yuc88j"  elapsed_s=0.097
[LOCK] set_ts: write done  points=8760   write_s=0.167
[SUBMIT] set_ts done       points=8760   elapsed_s=0.187
[LOCK] set_ts: write done  points=8760   write_s=0.026
[SUBMIT] set_ts done       points=8760   elapsed_s=0.026
[LOCK] set_ts: write done  points=17520  write_s=0.05
[SUBMIT] set_ts done       points=17520  elapsed_s=0.05
[LOCK] set_ts: write done  points=35040  write_s=0.063
[SUBMIT] set_ts done       points=35040  elapsed_s=0.063
[LOCK] set_ts: write done  points=105120 write_s=0.225
[SUBMIT] set_ts done       points=105120 elapsed_s=0.225
[SUBMIT] total done  stored_count=5  total_s=0.758
```

**结论**：
- 5 条边界的 submit 总耗时 **0.758 秒**，完全可接受
- 全程**未出现 `[LOCK] lock wait` 警告**，说明没有其他请求在竞争锁
- 每条 set_ts 的写入耗时在 16ms-225ms 之间，与点数成正比，正常

**H2（write_lock 阻塞）被排除。**

### 4.2 Node.js 侧 — projects.json 膨胀至 45 MB（确认根因）

```
[STORE] writing projects.json: 27805.3 KB, projects=7
[STORE]   project project-08e81daf boundaries JSON: 8451.9 KB, count=3
[STORE]     boundary b_mu3sz63d10wmst rawData=8760pts transformedData=175200pts layers=5
[STORE]     boundary b_mu3sz63d6y1zgj rawData=8760pts transformedData=175200pts layers=5
[STORE]     boundary b_mu3sz63dix3105 rawData=8760pts transformedData=175200pts layers=5
```

**随着新边界不断提交，projects.json 持续膨胀**：

| 时间点 | projects.json 总大小 | 触发原因 |
|---|---|---|
| 16:16:58 | **27,805 KB (27.1 MB)** | 页面加载，已有旧项目的 8760 边界 |
| 16:17:42 | **27,819 KB** | 编辑器保存画布（多次） |
| 16:17:43 | **36,512 KB (35.6 MB)** | 第一个新边界提交后 |
| 16:17:56 | **45,205 KB (44.1 MB)** | 第二个新边界提交后 |

**关键数据**：

- 单个 8760 点边界经 5 层 transform 后存入 projects.json：rawData=8760pts + transformedData=175,200pts = **~2.6 MB**
- 3 个这样的边界仅 boundaries 部分就占 **8.4 MB**
- 整个 projects.json 从 27 MB 膨胀到 44 MB
- **每次编辑器操作（保存画布、切换配置等）都触发一次完整的 27-44 MB JSON 序列化 + 写盘**

**H1（projects.json 内嵌大数组）被确认为根因。**

### 4.3 卡顿机制还原

```
projects.json = 44 MB
    │
    ├─→ 编辑器加载项目：readFile(44MB) + JSON.parse(44MB) + Vue reactive(全部 rawData/transformedData)
    │   → 首屏渲染严重卡顿
    │
    ├─→ 每次画布保存：updateProject → readFile(44MB) + JSON.stringify + writeFile(44MB)
    │   → 每次操作都卡
    │
    └─→ 创建计算任务：readProjectById(44MB) + JSON.stringify(44MB) 发给 Julia
        → 序列化 44MB JSON 字符串通过 HTTP 发送 → 后端完全卡住
```

---

## 5. 根因确认

**根因**：`BoundaryItem` 类型中的 `rawData` 和 `transformedData` 字段包含完整时序数组。前端边界页在提交到 boundary.db 后，紧接着将这些大数组通过 `PUT /api/v1/project/{id}/boundary` 存入了 `projects.json`。

**直接证据**：
- [types/boundary.ts:49-57](../types/boundary.ts#L49-L57) 定义 `rawData?: { values: number[] }` 和 `transformedData?: { layers: { values: number[] }[] }`
- [boundary/\[projectId\].vue:945-947](../app/pages/boundary/[projectId].vue#L945-L947) 提交后调用 `saveCurrentFormToBoundary()` + `flushProjectSyncPersist()`，将含大数组的 boundaries 写入项目
- [boundary.put.ts:13-16](../server/api/v1/project/[projectId]/boundary.put.ts#L13-L16) 原样存储 `body.boundaries` 到 projects.json

**根本原因**：时序数据没有遵循开发文档中"JSON 只保存边界配置、series ID、单位、来源摘要、变换参数和版本哈希"的设计原则（见开发文档总览 §4.4 数据存储），而是将完整数组同时存入了 JSON 和 SQLite，形成双重存储。

---

## 6. 修复方案

### 6.1 修改内容

**修改文件**：`server/api/v1/project/[projectId]/boundary.put.ts`

**修改方式**：在 BFF 保存边界配置时，用解构剥离 `rawData` 和 `transformedData`，只将配置元数据写入 projects.json。

```typescript
// 修改前：
const project = await updateProject(projectId, current => ({
  ...current,
  boundaries: body.boundaries
}))

// 修改后：
const lightBoundaries = body.boundaries.map(b => {
  const { rawData, transformedData, ...rest } = b as any
  return rest
})

const project = await updateProject(projectId, current => ({
  ...current,
  boundaries: lightBoundaries
}))
```

### 6.2 数据流变化

```
修改前：
  前端 submit → Julia boundary.db ✅
  前端 save → projects.json（含 rawData + transformedData）❌ 膨胀到 44MB

修改后：
  前端 submit → Julia boundary.db ✅（不变）
  前端 save → projects.json（仅含 id/name/meaning/boundaryMeta 等配置）✅ ~1-2MB
  前端 loadBoundary → /api/boundary/load → boundary.db → 按需加载 transformedData ✅
```

### 6.3 前端兼容性验证

`loadBoundary` 函数（[boundary/\[projectId\].vue:444](../app/pages/boundary/[projectId].vue#L444)）的数据恢复逻辑：

```
第469行：if (boundary.rawData)        → rawData.value = null（修复后 rawData 不在项目 JSON 中）
第481行：if (boundary.transformedData) → transformedData.value = null（同理）
第498行：随后调 /api/boundary/load    → 从 boundary.db 加载 → transformedData.value 被回填
```

`submitBoundary` 函数（第913行）的前置检查 `!transformedData.value` 只在当前会话内点击提交时触发，此时 `transformedData.value` 已由 `loadBoundary` 从 boundary.db 加载，不依赖 projects.json 存档。

## 7. 预期结果与副作用

### 7.1 预期改善

| 指标 | 修复前 | 预期修复后 |
|---|---|---|
| projects.json 大小 | 27-44 MB | 1-2 MB |
| 编辑器首屏加载 | 严重卡顿（数秒级） | 正常（<100ms） |
| 画布保存延迟 | 每次数秒 | 正常（<100ms） |
| 任务创建 | 后端卡死 | 正常（<1s） |
| 边界数据完整性 | 双重存储（JSON + SQLite） | SQLite 单一真值 |

### 7.2 已知副作用

| 副作用 | 影响范围 | 严重程度 | 后续处理 |
|---|---|---|---|
| 用户重新打开边界页时 rawData 预览图为空 | 边界配置页 | 低 | 需重新导入文件才能看到原始数据预览图表；transformedData 从 boundary.db 自动加载不受影响 |
| 已有旧项目的 boundaries 仍含大数组 | 历史项目 | 中 | 下次保存边界配置时自动清除；可考虑写一个迁移脚本主动清理所有项目的 boundaries 大数组 |
| `BoundaryItem.rawData` 字段实际不再被持久化 | 类型定义 | 低 | 后续从 `BoundaryItem` 类型中标记 rawData/transformedData 为运行时暂态字段，或迁移为独立 API |

### 7.3 后续优化建议（不在本次修复范围）

1. **boundary.db 同时存储原始数据**：在 import 阶段也写一份到 boundary.db，loadBoundary 可同时恢复 rawData 预览
2. **批量写入优化**：`_write_ts` 使用 SQLite 的 `INSERT ... VALUES` 批量绑定替代逐行 INSERT
3. **项目迁移脚本**：对已有项目扫描并清除 boundaries 中的 rawData/transformedData
4. **projects.json 分片存储**：长期方案将画布、边界、配置拆为独立文件，避免大项目整体读写

## 8. 调试日志保留建议

本次插入的 `[STORE]`、`[SUBMIT]`、`[LOCK]`、`[SEED]`、`[TASK-CREATE]` 日志在回归验证后：

- `[STORE]` 日志建议**保留**：projects.json 大小是前端性能的关键指标，可作为持续监控
- `[SUBMIT]` 日志建议**降级为 `@debug`**：生产环境不需要，调试时可开启
- `[LOCK]` 日志建议**保留 `@warn` 级别**（仅锁等待超 50ms 时输出）：锁竞争是并发问题的关键信号
- `[SEED]` 日志建议**降级为 `@debug`**：仅在排查 seed 问题时需要
- `[TASK-CREATE]` 日志建议**保留**：任务创建的 payload 大小直接影响后端响应时间

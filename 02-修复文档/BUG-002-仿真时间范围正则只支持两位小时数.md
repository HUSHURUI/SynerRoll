# BUG-002：仿真时间范围正则只支持两位小时数，8760h 任务默认降为 24h

> 修复日期：2026-09-16
> 状态：已定位、已修复、待回归验证
> 严重程度：P0 — 仿真范围被静默截断，计算结果错误
> 影响范围：所有仿真时间范围超过 99 小时的离线计算任务

---

## 1. 问题描述

**用户操作路径**：

1. 边界数据为 8760 小时（365 天全年逐小时数据）
2. 创建计算任务时，时间范围填写 `0:00-8760:00`
3. 任务启动后，运行到 `24:00` 即停止
4. 后端输出 `[END] 剩余时间不足一个 layer1 窗口，仿真结束`

**预期行为**：仿真应从 `0:00` 运行到 `8760:00`，覆盖全部 365 天。

---

## 2. 定位过程

### 2.1 追踪终止条件

通过搜索后端日志关键词 `剩余时间不足`，定位到 `backend/services/simulation_runner.jl:589`：

```julia
# ★ [数学业务] 外层循环：遍历 layer1 窗口
while true
    if layer1 !== nothing && layer1_length_min !== nothing
        window_end_min = time_label_to_minutes(sim_time) + layer1_length_min
        if sim_end_min !== nothing && window_end_min > sim_end_min   # ← 终止条件
            @info "task $(task_id): [END] 剩余时间不足一个 layer1 窗口，仿真结束"
            break
        end
    end
    # ... 求解当前窗口 ...
    sim_time = minutes_to_time_label(time_label_to_minutes(sim_time) + layer1_length_min)  # 推进到下一窗口
end
```

逻辑：每次循环将 `sim_time` 推进 `layer1_length_min`（一个 layer1 窗口长度），当剩余时间不足以容纳一个完整窗口时终止。

以 `sim_end_min = 8760×60 = 525,600` 分钟计算，如果 layer1 窗口为 24h（1440 分钟），循环应运行 365 次才结束，不会在 24:00 停止。

### 2.2 反推 simEndTime 实际值

既然循环在 24:00 停止，说明 `sim_end_min` 实际只有 `24×60 = 1440` 分钟。这意味着后端接收到的 `simEndTime` 是 `"24:00"` 而非 `"8760:00"`。

### 2.3 追踪前端发送值

查看任务创建链路：

```
前端 tasks/index.vue
  → simEndTime = `${parsedEndHour.value}:00`
  → POST /api/v1/task/create { simEndTime: "24:00" }
  → BFF → Julia /api/task/create { simEndTime: "24:00" }
```

追踪 `parsedEndHour` 的计算逻辑，定位到 [tasks/index.vue:805-809](../app/pages/tasks/index.vue#L805-L809)：

```typescript
const parsedEndHour = computed(() => {
  const match = /^(\d{1,2}):(\d{2})\s*[-~]\s*(\d{1,2}):(\d{2})$/.exec(timeRange.value.trim())
  if (!match) return 24        // ← 匹配失败时静默回退到 24
  return parseInt(match[3], 10)
})
```

---

## 3. 根因

**正则 `\d{1,2}` 只匹配 1~2 位数字。**

当用户输入 `0:00-8760:00` 时，正则引擎的匹配过程：

```
输入字符串：  0  :  0  0  -  8  7  6  0  :  0  0
正则期望：  \d{1,2} : \d{2} - \d{1,2} : \d{2} $

匹配 "8760" 的过程：
  尝试 \d{1,2} 贪婪匹配 "87" → 下一个期望 ":"，实际为 "6" → 失败
  回退 \d{1,2} 匹配 "8"    → 下一个期望 ":"，实际为 "7" → 失败
  → 整个正则不匹配，match = null
```

`match = null` → `return 24`（默认值）→ `simEndTime = "24:00"` → 后端只跑 24 小时。

**对比**：同一文件的 `validateTimeRange` 函数（[第 769 行](../app/pages/tasks/index.vue#L769)）已使用 `\d+`，校验能通过但解析时静默降级，形成隐蔽 bug。

---

## 4. 修复方案

### 4.1 修改内容

**文件**：`app/pages/tasks/index.vue` — `parsedEndHour` computed 属性

```typescript
// 修改前：
const match = /^(\d{1,2}):(\d{2})\s*[-~]\s*(\d{1,2}):(\d{2})$/.exec(...)

// 修改后：
const match = /^(\d+):(\d{2})\s*[-~]\s*(\d+):(\d{2})$/.exec(...)
```

将捕获小时数的正则从 `\d{1,2}` 改为 `\d+`，支持任意位数的小时值。

### 4.2 后端兼容性确认

Julia 侧 `time_label_to_minutes`（[timestr_utils.jl:38](../backend/utils/timestr_utils.jl#L38)）已使用 `\d+`，可正确解析 `"8760:00"` → `525600` 分钟。后端无需修改。

---

## 5. 预期结果与副作用

### 5.1 预期改善

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `0:00-8760:00` | 静默降为 `0:00-24:00`，只跑 1 天 | 正确跑满 365 天 |
| `0:00-168:00`（一周） | 静默降为 `0:00-24:00` | 正确跑满 7 天 |
| `0:00-24:00`（一天） | 正常 | 正常（无变化） |
| `0:00-48:00`（两天） | 静默降为 `0:00-24:00` | 正确跑满 2 天 |

### 5.2 副作用

无。`\d+` 完全兼容原有的 1~2 位数字场景，只是扩展了上界。
